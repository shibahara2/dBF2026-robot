# チェックイン入口 設計仕様 (2026-09-29)

## 背景・目的

チェックインを始める手段が3つになった。

- **画面操作**: キオスクの「チェックインを開始」ボタン
- **画像**: Themisの画像をVLMで判定し、話しかけている人がいれば
  `POST /api/visual/start`（Issue #5）
- **発話**: `voice_ui/` がマイクから名前を聞き取り、`POST /api/checkin
  {"name": ...}` で直接チェックイン

発話だけが画面を通らず、予約の照合も確認もせずにサイクルを開始している。
`docs/state_machine.pdf` の「なかみ」はチェックインを
「開始画面 → 予約確認画面 → 完了画面」の3画面で定義しており、音声は
「マイク・スピーカーを繋げて音声IF」として画面の入力手段に位置付けられて
いる。現在の発話入口はこの想定からずれている。

また、デバッグ画面 (`/debug`) で、どの入口から始まり、どこまで進んだかを
ライブで確認したい。

本仕様は次の2点を定める。

1. チェックインのシーケンスを画面の1本に統一し、画像・発話は
   「チェックイン開始」だけを叩ける入口とする。
2. 入口と進み具合を状態機械に記録し、デバッグ画面に表示する。

## シーケンス

```
チェックイン開始 ──→ 予約選択 ──→ チェックイン完了
  ├ 画面操作：開始ボタン          （画面）      （画面）
  ├ 画像　　：VLM検知（POST /api/visual/start）
  └ 発話　　：「チェックイン」を含む発話（POST /api/voice/start）
```

| 段階 | 画面 (`state_machine.pdf`) | 何が起きたら到達するか |
|---|---|---|
| チェックイン開始 (`start`) | 開始画面 → 検索画面 | 入口ごとに異なる（下表） |
| 予約選択 (`select`) | 予約確認画面 | キオスクで予約が選ばれた（検索結果1件の自動選択を含む） |
| チェックイン完了 (`checkin`) | 完了画面 | `POST /api/checkin` が受け付けられ、サイクルが始まった |

| 入口 (`entry_source`) | 「チェックイン開始」の判定方法 |
|---|---|
| `screen` | キオスクの開始ボタンが押された |
| `visual` | VLMが「話しかけている」と判定し、`POST /api/visual/start` が受け付けられた |
| `voice` | 確信度を通過した発話に開始キーワード（既定「チェックイン」）が含まれ、`POST /api/voice/start` が受け付けられた |

- 入口の違いは「チェックイン開始」の判定方法だけ。どの入口でも結果は同じで、
  キオスクが検索画面に切り替わる。
- 名前・予約番号・電話番号の入力、予約選択、確定は、どの入口でも画面で行う。
- 予約検索そのものは段階として扱わない（記録しない）。

## スコープ

対象:

- `POST /api/voice/start` の新設（`/api/visual/start` と同じ振る舞い）
- `voice_ui` を「開始キーワードの検知 → `/api/voice/start`」に変更
- 入口と段階の記録（状態機械のsnapshot）
- キオスクからの段階報告（開始ボタン、予約選択、戻る）
- デバッグ画面の「チェックイン入口」欄
- 画像パイプラインでの409/429の扱い（想定内の応答にする）

対象外:

- 検索語（名前・予約番号・電話番号）の音声入力。将来
  `POST /api/voice/query` を追加できる形にだけしておく。
- マイクの状態連動ゲーティング（`2026-09-13-voice-ui-design.md` と同じく
  対象外のまま）。
- `voice_ui` の `FLASK_BASE_URL` 既定値（`:5000`）と `run.py` のポート
  （`:5100`）の不一致。別途対応する。

## 状態の記録

### snapshotのフィールド

`app/state_machine.py` のsnapshotに次の3つを持つ。

| フィールド | 値 |
|---|---|
| `entry_source` | `screen` / `visual` / `voice` / `null` |
| `entry_stage` | `start` / `select` / `checkin` / `null` |
| `entry_at` | 最後に記録した時刻（UTC、`YYYY-MM-DDTHH:MM:SSZ`）/ `null` |

- 3つとも `null` のときは「進行中の入口なし」。
- 「進行中の入口」は `entry_stage` が `start` か `select` のもの。

### 記録の規則

| 操作 | 条件 | 結果 |
|---|---|---|
| 開始（画像・発話） | 待機中（`waiting`/`awaiting_checkin`）で、進行中の入口がない、または最終記録から `ENTRY_IDLE_SECONDS` 以上たっている | `(source, start)` を記録。キオスクへ `ui_action: start_checkin` を配信 |
| 開始（画像・発話） | 上記以外 | 何も記録・配信しない（409） |
| キオスクの開始ボタン | 待機中 | 進行中の入口があればその入口のまま `start`、なければ `(screen, start)` |
| キオスクの予約選択 | 待機中 | 進行中の入口があればその入口のまま `select`、なければ `(screen, select)` |
| キオスクの「検索に戻る」 | 待機中で `select` | 入口はそのまま `start` に戻す（開始ボタンと同じ報告で行う） |
| キオスクの「戻る」（開始画面へ） | 待機中 | 入口の記録を消す |
| `POST /api/checkin`（予約ID） | 受け付けられた | 進行中の入口があればその入口、なければ `screen` で `checkin` |
| サイクル終了（待機中に戻る）・エラーからのリセット | — | 入口の記録を消す |

- 待機中でないとき（サイクル中・エラー中）の報告は記録しない。
- 画像・発話の開始を、進行中の入口があるときに受け付けないのは、画面で
  操作中の人を検索画面へ飛ばさないため。キオスクから離れた人の記録で
  ずっと塞がらないよう、`ENTRY_IDLE_SECONDS`（既定60秒）を過ぎた記録は
  進行中とみなさない。
- 画像・発話の開始の連打は、既存の `VisualStartGate`（クールダウン、
  `VISUAL_START_COOLDOWN_SECONDS`）で入口ごとに抑制する（429）。

## API

### `POST /api/voice/start`（新設）

`/api/visual/start` と同じ入出力。本体は画像と共通の関数にする。

| ステータス | 意味 |
|---|---|
| 202 | 記録して `ui_action: start_checkin` を配信した |
| 409 | 待機中でない、または進行中の入口がある |
| 429 | クールダウン中 |

### `POST /api/visual/start`（変更）

- 409の条件に「進行中の入口がある」を加える。

### `POST /api/entry`（キオスク専用に変更）

キオスクがサーバーから見えない操作を報告する。

- リクエスト: `{"stage": "start" | "select"}`
- 入口 (`source`) は送らない。サーバーが上記の規則で決める。
- 202: 記録した / 409: 待機中でない / 422: `stage` が不正

### `DELETE /api/entry`（そのまま）

- 「戻る」で開始画面に戻ったときに呼ぶ。入口によらず記録を消す。
- `{"cleared": true | false}` を返す。

### `POST /api/checkin`（変更）

- 名前だけのチェックイン（`{"name": ...}`）を廃止し、`reservation_id` を
  必須にする。`reservation_id` がなければ422。
- 名前だけのチェックインの唯一の利用者だった `voice_ui` が使わなくなるため。

## キオスク (`app/static/app.js`)

| 操作 | 報告 |
|---|---|
| 開始ボタン | `POST /api/entry {"stage": "start"}` |
| 予約が選ばれた（`selectReservation`） | `POST /api/entry {"stage": "select"}` |
| 「検索に戻る」 | `POST /api/entry {"stage": "start"}` |
| 「戻る」（開始画面へ） | `DELETE /api/entry` |

- 報告はデバッグ表示のためだけなので、失敗しても画面の動作は止めない。
- 報告によって配信されるsnapshotは `awaiting_checkin` のままなので、キオスクの
  画面は変わらない。

## 音声IF (`voice_ui/`)

### 入力系

```
mic → VAD → Whisper → 確信度判定 → 開始キーワード判定 → POST /api/voice/start
```

- 確信度を通過した発話に、開始キーワードのどれかが含まれていれば
  `/api/voice/start` を呼ぶ。含まれていなければ何もしない（ログのみ）。
- 開始キーワードは環境変数 `VOICE_START_KEYWORDS`（カンマ区切り、既定
  `チェックイン`）。照合はNFKC正規化・空白除去・小文字化してから部分一致で行う。
- `CheckinClient.checkin(name)` を `VoiceStartClient.start()` に置き換える。
  202 → `accepted`、409 → `not_available`、429 → `rate_limited`、
  それ以外は既存と同じ分類（`timeout` / `connection_error` / `server_error`）。
- 削除するもの: `voice_ui/name_extract.py`、名前抽出の報告
  （`report_entry("speech" | "transcribed")`）、名前だけのチェックイン。

### 出力系（読み上げ）

- `ProgressAnnouncer` が、`entry_source == "voice"` かつ `entry_stage` が
  `start` に変わったsnapshotを受けたら、
  「画面にお名前、予約番号、または電話番号を入力してください」と読み上げる。
  音声の案内をSSEで駆動することで、入力系と出力系を独立させたままにする。
- `type` を持つイベント（`ui_action` など）はsnapshotではないので無視する。
  現在は `ui_action` を受けると直前の `step` の記憶が `None` に戻る不具合がある。

## デバッグ画面 (`/debug`)

シーケンス図の上に「チェックイン入口」欄を置く。

```
チェックイン開始            予約選択      チェックイン完了
 ┌ 画面操作：開始ボタン ┐
 ├ 画像　　：VLM検知 ───┼──→ [予約選択] ──→ [チェックイン完了]
 └ 発話　　：発話検知 ───┘
最終更新: 10:50:09
```

- 「チェックイン開始」列は3つの入口を縦に並べ、判定方法を添える。
  `entry_source` の行を強調する。
- 「予約選択」「チェックイン完了」は1つずつ（共通）。
- 現在の `entry_stage` を塗りつぶし、そこまでの段階を枠線で示す
  （既存のシーケンス図と同じ青 `#1a73e8`）。
- 入口の記録がないときは何も強調しない。

## エラーハンドリング

| 状況 | 振る舞い |
|---|---|
| キオスクの報告が失敗 | 無視（画面の動作は続ける） |
| `/api/voice/start` が409/429 | `voice_ui` はログのみ。読み上げない |
| `/api/voice/start` に接続できない | `voice_ui` は警告ログを出して待ち受けを続ける |
| `/api/visual/start` が409/429 | 画像パイプライン (`themis_video/pipeline.py`) は現在これを例外として処理エラーに数え、スタックトレースを毎回出す。409/429は想定内の応答として扱い、INFOログだけにする |
| 開始したが誰も予約を選ばない | 記録は残る。`ENTRY_IDLE_SECONDS` 経過後は画像・発話の開始を再び受け付ける |

## テスト方針

- 状態機械: 各規則（入口の引き継ぎ、`ENTRY_IDLE_SECONDS`、待機中以外の無視、
  サイクル終了・リセットでの消去）を単体テストする。時刻は既存の `now`
  注入で固定する。
- 画像パイプライン: 409/429を受けても例外にならず、処理エラーに数えないこと。
- ルート: `/api/voice/start`（202/409/429）、`/api/visual/start` の409追加、
  `/api/entry` の `stage` 検証、`/api/checkin` の名前だけ廃止。
- `voice_ui`: キーワード判定（正規化・部分一致・設定）、`VoiceStartClient` の
  ステータス分類、`ProgressAnnouncer` の案内読み上げと `type` 付きイベントの無視。
- E2E: 既存の画像E2E（`tests/test_visual_e2e.py`）を新しい記録に合わせる。
- デバッグ画面: 入口欄の要素と、`debug.js` がsnapshotの3フィールドを使うこと。

## 既存の作業ブランチとの関係

作業ツリーには、この仕様の前段として実装した入口記録
（段階名 `start/search/checkin` など、発話の `speech/transcribed` 報告を含む）
が未コミットで残っている。本仕様で段階名・API・発話の扱いが変わるため、
その実装はこの仕様に合わせて作り直す。
